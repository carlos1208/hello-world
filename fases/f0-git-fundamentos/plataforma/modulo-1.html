El commit es inmutable, y de ahí sale todo lo demás

Git no guarda diferencias: guarda objetos direccionados por el hash de su propio contenido. Un blob es el contenido de un archivo sin nombre; un tree es la carpeta que le pone nombre; un commit es un tree más el padre, el autor y el mensaje.

Como el hash del padre entra en el cálculo del hash del hijo, cambiar un commit cambia todos los que vienen después. Nada se edita: amend, rebase y cherry-pick crean objetos nuevos y mueven la rama. Los viejos siguen en la base de objetos, sin nombre que los apunte.

Git casi nunca borra. Solo pierde el nombre

Cada vez que una referencia se mueve, Git lo anota en .git/logs/HEAD. Ese registro es el reflog, y registra dónde estuvo HEAD, no qué commits existen. Cuando un reset --hard deja commits huérfanos, los objetos siguen ahí: lo único que perdiste fue la referencia que los apuntaba.

Por eso el reflog se aprende antes que rebase: es la red debajo del trapecio. Un ingeniero que conoce el reflog experimenta; uno que no, evita la herramienta.

Un historial que se pueda bisecar

Bisect te deja parado en un commit y te pregunta qué pasó ahí. Si ese commit se llama arreglo2, el diagnóstico no avanzó. Si se llama «Simplificar el cálculo del MTTR», el diagnóstico está hecho.

Rebase interactivo es lo que convierte un historial de exploración en uno de decisiones, antes de publicarlo. La regla que no se rompe: nunca reescribas lo que otros ya tienen.
